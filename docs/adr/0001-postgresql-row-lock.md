# ADR-0001: ใช้ PostgreSQL + ล็อกแถวร้าน + Read Committed กันจองเกินที่นั่ง

วันที่: 2026-10-02 · สถานะ: Accepted · ผู้ตัดสินใจ: ผู้พัฒนา (Final Exam)

## บริบท (Context)

- จองแบบนับที่นั่งรวมทั้งร้าน: ทุกจุดเวลาในช่วงที่จอง ผลรวมคนต้องไม่เกิน `capacity` (ไม่ใช่แค่ "ห้ามทับ")
- หลายคนจองร้านเดียวกันช่วงเดียวกันได้พร้อมกัน และเจ้าของลดที่นั่งหรือลบร้านพร้อมกับมีคนจองได้
- การจองใหม่ยังไม่มีแถวในตาราง (phantom) จึงล็อกแถวการจองเพื่อกันกันเองไม่ได้
- ต้องอธิบายได้ง่ายในการสัมภาษณ์

## ทางเลือกที่พิจารณา

1. **ล็อกแถวร้าน** `SELECT … FROM restaurants WHERE id = $1 AND deleted_at IS NULL FOR UPDATE` + Read Committed
2. Exclusion constraint (`EXCLUDE USING gist`) — กันได้แค่ "ห้ามทับ" ไม่ใช่ "ผลรวมไม่เกิน"
3. Serializable isolation + retry — ถูกต้องแต่ต้องเขียน retry ทุกจุด และอธิบายยากกว่า
4. ล็อกทั้งตาราง `LOCK TABLE bookings` — ถูกต้องแต่ทุกร้านในระบบต้องต่อคิวเดียวกัน
5. ส่งการจองเข้า queue แล้วให้ worker ตัดสินทีละรายการ — ผู้ใช้ไม่รู้ผลทันที เกินจำเป็นสำหรับขนาดงาน

## การตัดสินใจ (Decision)

เลือกข้อ 1 ทุก pipeline ที่อ่านค่าร้านเพื่อตัดสินใจ (จอง, แก้, ตั้งค่า, ลบร้าน, เพิ่ม/ลบรูป, พักรับจอง)
เรียก `db.LockRestaurant` เป็นคำสั่งแรกใน transaction และอ่านค่าร้าน**หลัง**ล็อกเท่านั้น ลำดับการล็อกคือ ร้าน → การจอง เสมอ
ใช้ Read Committed (ระบุชัดใน `db.WithTx`) ห้ามใช้ Repeatable Read หรือ Serializable ในงานที่ล็อกแถวร้าน
ยกเลิกการจองไม่ล็อกร้าน เพราะมีแต่ทำให้ที่นั่งว่างขึ้น ใช้ `UPDATE … WHERE status = 'active' AND now <= cancel_deadline` คำสั่งเดียว

## ผลที่ตามมา (Consequences)

- \+ จองเกินไม่ได้ พิสูจน์ด้วย `TestConcurrent*` แบบ `-race -count=100` และ mutation test (เอา `FOR UPDATE` ออกหรือใช้ Repeatable Read → จองเกินจริง)
- \+ ร้านต่างกันทำงานขนานกัน และยังถูกต้องเมื่อรัน API หลายตัว เพราะ lock อยู่ใน DB
- \+ อธิบายเป็นลำดับเดียวได้: ล็อก → อ่าน → ตัดสิน → เขียน
- − ร้านที่ดังมากจองพร้อมกันจะต่อคิวกันที่แถวเดียว (ประมาณการว่ารับได้หลักร้อยรายการ/วินาทีต่อร้าน ซึ่งเกินพอ)
- − ห้ามลืมเรียก `LockRestaurant` ในฟีเจอร์ใหม่ที่อ่านค่าร้านเพื่อตัดสิน (กันด้วย code review และ concurrency test)
