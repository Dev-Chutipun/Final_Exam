# Prompt สำหรับสั่ง Claude Code ทีละขั้น

**วิธีใช้**
1. วาง `CLAUDE.md` ที่ root ของ repo และโฟลเดอร์ `docs/` ทั้งโฟลเดอร์
2. ส่ง prompt ทีละอัน ตามลำดับ **อย่าส่งหลายขั้นพร้อมกัน**
3. จบแต่ละขั้น Claude Code ต้องรัน build, vet และ test จริงบนเครื่องนี้ แล้ว commit · อ่านสรุปและผล test ก่อนส่ง prompt ถัดไป
   งานที่ต้องใช้เบราว์เซอร์ Claude Code จะให้ขั้นตอนทดสอบด้วยมือ ทำแล้วรายงานกลับด้วย prompt **"ผลทดสอบด้วยมือ"**
4. เจอ Checkpoint ให้ใช้ prompt ในหมวด "Checkpoint" ก่อนไปต่อ
5. ขึ้น session ใหม่เมื่อไหร่ ให้เริ่มด้วย prompt "กลับมาทำงานต่อ"

## Checkpoint (ใช้แทนการอ่านโค้ดเองทั้งหมด)

### แม่แบบ
```
Checkpoint [ตัวอักษร]: อธิบาย [หัวข้อ] จากโค้ดจริงในโปรเจกต์ เป็นภาษาไทย ทีละส่วน
ชี้บรรทัดสำคัญพร้อมเหตุผลว่าทำไมเขียนแบบนี้ และถ้าเขียนแบบอื่นจะพังอย่างไร
จากนั้นตั้งคำถาม 3 ข้อแบบที่กรรมการสัมภาษณ์น่าจะถาม ห้ามเฉลยจนกว่าฉันจะตอบ
แล้วตรวจคำตอบของฉันและบอกจุดที่ยังเข้าใจไม่ครบ
```

| Checkpoint | หัวข้อที่ใส่ในแม่แบบ |
|---|---|
| A | MaxLoad, PeakAll และเหตุผลที่ใช้ช่วงเวลาแบบ half-open (ใช้ตัวอย่างสไลด์ 7–8) |
| B | ลำดับ transaction ของการจองใหม่ ทำไมล็อกแถวร้าน ทำไมต้องอ่านค่าร้านหลังล็อก และทำไมห้าม Repeatable Read |
| C | Bayesian average ในการเรียงร้าน และทำไมใช้ unique constraint กันรีวิวซ้ำแทนการเช็คก่อน |
| D | flow login ตั้งแต่กดปุ่มจนได้ session, หน้าที่ของ state/nonce/PKCE, session เก็บที่ไหน และกัน CSRF อย่างไร |
| E | หน้าไหนเป็น Server/Client Component เพราะอะไร, cookie เดินทางจาก browser ถึง Go อย่างไร และทำไมไม่ใช้ Server Actions |

## Prompt ช่วยงาน

### กลับมาทำงานต่อ (เริ่ม session ใหม่)
```
อ่าน CLAUDE.md และ docs/00-overview.md §6 แล้วดู git log กับผล go test ./... 
บอกว่าตอนนี้เราอยู่ขั้นไหนของเอกสารไหน ขั้นถัดไปคืออะไร และมีอะไรค้างอยู่ ยังไม่ต้องเขียนโค้ด
```

### ผลทดสอบด้วยมือ
```
ผลทดสอบด้วยมือของขั้น [ชื่อขั้น]:
[ข้อที่ผ่าน / ข้อที่ไม่ผ่าน + สิ่งที่เห็น หรือภาพหน้าจอ]
ข้อที่ไม่ผ่าน: วิเคราะห์สาเหตุ แก้ รัน test อัตโนมัติที่เกี่ยวข้องให้ผ่าน แล้วบอกว่าต้องทดสอบด้วยมือซ้ำข้อไหน
```

### แก้ bug
```
พบ bug: [อาการ + ขั้นตอนทำซ้ำ]
เขียน test ที่จำลอง bug นี้ให้พังก่อน แสดงให้ฉันเห็นว่าพัง แล้วค่อยแก้ให้ test ผ่าน
อธิบายสาเหตุเป็นภาษาไทย 3–5 บรรทัด
```

### ตรวจงานเทียบสเปก
```
ตรวจโค้ดที่เปลี่ยนตั้งแต่ commit [hash] เทียบกับ [ไฟล์ spec และหัวข้อ]
รายการจุดที่ไม่ตรงสเปก, test ที่ขาด และสิ่งที่ทำเกินสเปก ห้ามแก้อะไรจนกว่าฉันจะเลือก
```

### เวลาไม่พอ
```
เหลือเวลา [N] วัน ดู docs/00-overview.md §1 และ §6
เสนอว่าควรตัดงานระดับ B ข้อไหนออก และงานระดับ A ข้อไหนที่เสี่ยงไม่เสร็จ พร้อมเหตุผล
```
